## 今回の動作

- 件数一致だけでは同期正常にしない。日付・状態・径・期限・履歴などの正規化した内容を最終取得／保存後取得と比較する。
- 同じ件数の変更、削除、保存確認中に加わった編集は未反映として残す。一部未反映やエラーは内容一致でも正常に戻さない。
- バッジは「反映確認済み」。サーバーを常時監視している意味ではなく、最終確認時点の一致を示す。詳細で確認日時を表示する。
- 再ログインの読込みで端末と表に差があれば端末の変更を保持する。表を黙って上書きする操作もしない。オフラインの項目別競合解決は別の残課題。
- 普段の表示は3セットの作業確認とロール一覧を中心にする。「詳しい確認を開く」で診断・月次出力・補助欄を戻せる。工作課モードの既存表示は保つ。

## 認証の境界

`js/identity.js` が本人確認と認証付き通信を担当する。`js/deployment-config.js` は公開可能な接続情報だけを保持する。ロールの業務ロジックは認証サービスを直接呼ばない。

GoogleアカウントでFirebase Authenticationへログインし、IDトークンをPOST本文でGASへ送る。URL、localStorage、サービスワーカーにはトークンを保存しない。GASはGoogleの本番用accounts:lookupへトークンを渡して本人確認を委譲し、プロジェクト・発行者・期限・Googleプロバイダー・UID・確認済みメール・失効時刻を照合する。JWTをデコードしただけでは許可しない。デバッグ用tokeninfoには依存しない。

GASのScript PropertiesにUID別の許可権限を置く。`reader`は読取り、`editor`は通常編集、`admin`は追加の管理処理を許可する。ブラウザの表示フラグや担当者の選択はアクセス権にならない。保存結果の照会も保存した利用者だけに制限する。公開GETのデータ取得・旧保存・デバッグ更新は拒否する。

業務データは従来どおり端末内にも残るため、端末ストレージを暗号化したことにはならない。既存の未反映変更を消さないためログアウト時に消去せず、異なるUIDでは同じ端末データを読み込ませない。共有端末でのアカウント切替・データ隔離は運用確認が必要。失効後のAPI操作は毎回の本人確認で拒否する。

## 検証環境の準備

1. 管理するGoogleアカウントでFirebaseプロジェクトとWebアプリを用意し、AuthenticationのGoogleプロバイダーを有効化する。課金・契約を勝手に有効化しない。
2. 検証フロントエンドの実際のホストだけを承認済みドメインへ登録する。接続設定の `firebase` にコンソールが示す公開設定を入力し、`apiEndpoint` は検証GASのURLにする。秘密鍵・サービスアカウントJSON・利用者一覧は公開コードへ置かない。
3. 同じプロジェクトのGAS Script Propertiesに `ROLL_AUTH_PROJECT_ID`、`ROLL_AUTH_WEB_API_KEY`、`ROLL_AUTH_USERS` を設定する。利用者一覧の形式は `{"FirebaseのUID":"admin"}`。UIDをFirebaseで本人確認して登録する。未登録者にはアクセスを許可しない。APIキーのAPI制限・ブラウザ用とサーバー用の制限の違いも確認する。
4. 非公開テストブックに接続した新バージョンのGASと検証フロントエンドを組み合わせる。本番の公開設定・既存デプロイ一覧は別途確認する。
5. 許可／未許可／閲覧専用／無効化したアカウントで検証する。認証付きPOST→リダイレクト→JSON受信を実ブラウザで確認する。CORSが通らない場合は未認証GETやno-corsへ戻さず、認証付きの同一オリジン中継など通信構成を変更する必要がある。
6. 日付訂正、空欄訂正、失敗後の再試行、保存中の追加変更、ログアウト・再ログイン、PWA更新、スマホ表示・工作課表示を確認する。

GASの古い公開デプロイが残れば新ログインの保護対象外になる。移行時はそれらの停止／更新も確認する。認証サーバーだけ、画面だけを先に本番へ反映すると旧クライアントが使えなくなるため、保全と切替手順が必要。
